# Commands

The full command reference, moved from CLAUDE.md (ADR 0033). CLAUDE.md keeps the everyday
commands; keep this file current when a phase adds a command.

Run from the repository root. pnpm comes from the `packageManager` field through
corepack (`corepack enable` once); the user's global corepack cannot run pnpm 12
(ADR 0010). Integration and e2e tests need Docker (Testcontainers) and network.

| Purpose | Command |
| --- | --- |
| Install | `pnpm install` (CI: `pnpm install --frozen-lockfile`) |
| Build | `pnpm build` |
| Type-check | `pnpm typecheck` |
| Lint (incl. package boundaries) | `pnpm lint` |
| Unit tests | `pnpm test` |
| Integration tests | `pnpm test:int` |
| End-to-end tests | `pnpm test:e2e` |
| Single package / single test | `pnpm --filter @aiops/<pkg> test` (or `test:int`, `test:e2e`); one file: `cd <pkg> && pnpm exec vitest run --project <unit\|integration\|e2e> <path>` |
| Full CI run locally | `bash scripts/ci.sh` |
| Phase 1 acceptance (fresh clone of HEAD, Compose) | `bash scripts/acceptance/phase-1.sh` |
| Phase 2 acceptance (fresh clone of HEAD, Compose, real Keycloak logins) | `bash scripts/acceptance/phase-2.sh` |
| Phase 3 acceptance (fresh clone of HEAD, Compose, Magento sandbox, page login, credential entry) | `bash scripts/acceptance/phase-3.sh` (brings the sandbox up and seeds it itself; not in CI: needs the sandbox) |
| Phase 4 acceptance (fresh clone of HEAD, Compose, Magento sandbox, change-set preparation) | `bash scripts/acceptance/phase-4.sh` (brings the sandbox up and seeds it itself; not in CI: needs the sandbox) |
| Phase 5 acceptance (fresh clone of HEAD, Compose with two workers, Magento sandbox, 3000-item run with killed workers, drift) | `bash scripts/acceptance/phase-5.sh` (brings the sandbox up and seeds it itself, including 3000 umbrella products; not in CI: needs the sandbox) |
| Phase 6 acceptance (fresh clone of HEAD, Compose, Magento sandbox, approvals by alice/dave on the pages, tampered item, expiry, Mailpit) | `bash scripts/acceptance/phase-6.sh` (brings the sandbox up and seeds it itself; not in CI: needs the sandbox; about 10 minutes, including the 3-minute expiry wait) |
| Phase 7 acceptance (fresh clone of HEAD, Compose, Magento sandbox, terminal client, reference host in headless Chromium, exclusion, export, widget approval) | `bash scripts/acceptance/phase-7.sh` (brings the sandbox up and seeds it itself; not in CI: needs the sandbox; needs `pnpm install` and the cached Chromium for Playwright 1.65.1, otherwise `pnpm --filter @aiops/tooling exec playwright install chromium`; prints the optional manual steps for Claude Desktop and ChatGPT, ADR 0041) |
| Phase 7 manual-check configuration (sandbox URL, `record_threshold: 2`, `allow_widget: false`) for the optional Claude Desktop and ChatGPT checks | `bash scripts/acceptance/phase-7.sh --manual-config <dir>`, then start Compose with `AIOPS_ACCEPT_CONFIG_DIR=<dir>` and `-f compose.yaml -f scripts/acceptance/phase-7.compose.yaml` (full steps printed at the end of the acceptance run) |
| Phase 8 acceptance (fresh clone of HEAD, Compose, Magento sandbox; group 1 rollback on the page, group 2: audit chain (needs group 1's audit rows; alters one row as superuser, verify must fail, then restores it), group 3: configuration apply (grants dave an operation in the generated `roles.yaml`, `config diff`, `config apply`, tools/list follows without restart, audit rows; needs no other group), later group observability) | `bash scripts/acceptance/phase-8.sh` (all groups), `AIOPS_ACCEPT8_GROUPS=1 bash scripts/acceptance/phase-8.sh` (rollback only), `AIOPS_ACCEPT8_GROUPS="1 2" bash scripts/acceptance/phase-8.sh` (rollback and audit chain), `AIOPS_ACCEPT8_GROUPS="1 2 3" bash scripts/acceptance/phase-8.sh` (up to configuration; group 4 is not defined yet and fails when selected); brings the sandbox up and seeds it itself; not in CI: needs the sandbox |
| Widget bundles (MCP Apps, single-file HTML) | `pnpm --filter @aiops/widgets build:widgets` writes `packages/widgets/dist/ui/{changeset,approval}.html` (part of `build`); the `api` image ships them in `/app/widgets` (`AIOPS_WIDGET_DIR`) |
| Reference MCP Apps host (headless Chromium, MCP-5, UI-6) | `pnpm --filter @aiops/tooling build:widget-host`, then `AIOPS_MCP_TOKEN=… node tooling/acceptance/widget-host.mjs <mcp-url> list \| render --tool <name> [--args JSON] [--exclude N] [--submit] [--decide approve] [--open-page] [--wait-terminal S]` (prints one JSON line) |
| Development mail sink (Mailpit) | web UI and API at `http://localhost:8025` (`AIOPS_MAILPIT_PORT`); list messages: `curl -s http://127.0.0.1:8025/api/v1/messages`; fetch one: `/api/v1/message/<ID>` (the search endpoint tokenizes UUIDs, so it does not find a change-set id) |
| Compose up / down / logs | `docker compose up -d --build --wait` / `docker compose down` (`-v` drops data) / `docker compose logs -f <service>` |
| Database migrate | Runs on `api` start (NFR-5). New migration: edit `packages/db/src/schema.ts`, then `pnpm --filter @aiops/db db:generate --name <name>` (custom SQL: add `--custom`) |
| Record a workflow history fixture | `pnpm --filter @aiops/worker record-history <scenario>` (changesetWorkflow, encrypted with the test key, Temporal identity `aiops-recorder`; no argument lists the scenarios; refuses to overwrite) |
| Worker environment (Compose sets it) | `DATABASE_URL`, `AIOPS_CONFIG_DIR`, `AIOPS_PRESET_DIRS`, `AIOPS_MASTER_KEYS` as for `api`, plus `AIOPS_TEMPORAL_KEYS` (`<version>:<base64 of 32 bytes>`, comma-separated, highest encrypts; SEC-4) and `TEMPORAL_ADDRESS`/`TEMPORAL_NAMESPACE`/`TEMPORAL_TASK_QUEUE`; optional `AIOPS_PREPARE_TIMEOUT_MS` (default 3600000, > 60000), `AIOPS_BATCH_HEARTBEAT_MS` (> 10000), `AIOPS_BATCH_TIMEOUT_MS`, `AIOPS_BATCH_MAX_ATTEMPTS`, `AIOPS_RETRY_INITIAL_MS`, `AIOPS_RETRY_MAX_MS` (never set empty); notifications (NTF-1): `AIOPS_SMTP_URL` (`smtp://host:port` or `smtps://`, optional; without it email notifications fail with `channel_unconfigured`), `AIOPS_MAIL_FROM`, `AIOPS_PUBLIC_URL` (links in notifications). The worker also runs the notification dispatcher (every 5 s, NTF-3). The worker starts after `api` is healthy (migrated) and logs `worker polling` |
| Smoke workflow through the payload codec | `docker compose exec -T worker node dist/smoke-cli.js <message>` prints `{"echoed":"<message>"}` |
| Config CLI (validate) | `pnpm build` once, then `pnpm aiops-config validate deploy/config` (exit 0 valid, 1 invalid, 2 usage); in the image: `node node_modules/@aiops/config/dist/cli.js validate /etc/aiops/config` |
| Configuration revisions (CFG-3, CFG-4) | `pnpm aiops config diff <dir> [--preset-dir <dir>]...` compares `<dir>` with the active revision (prints `+`/`-`/`~ <kind> <id>: <keys>` lines and `hash <old> -> <new>`; exit 0, 1 invalid or unreadable, 2 usage); `pnpm aiops config apply <dir> [--preset-dir <dir>]... [--actor <name>]` stores `<dir>` as the new active revision, audited as `cli:<name>` (exit 0, also for `No changes`; 1 invalid or a concurrent apply); `pnpm aiops config explain --operation <id> --groups <g1,g2,...> [--subject <s>] [--args <json>] [--records <n>]` is a dry policy evaluation against the active revision (POL-7): checks `--args` (default `{}`) against the input schema, then prints `effect`, `rule`, `roles`, `reason`, `detail`, and for an allowed write the `approval` line for `--records` (default 1) changes; writes nothing (exit 0 allow, 1 deny or `invalid_arguments`, 2 usage, no revision or `configuration_mismatch`). All need `DATABASE_URL`; in the image: `docker compose exec -T api node dist/cli.js config diff\|apply /etc/aiops/config` (`config explain …` likewise) (`--actor` defaults to `$USER`). Running `api` and `worker` follow an applied revision within seconds, without a restart |
| Configuration files vs revisions | Files in `AIOPS_CONFIG_DIR` only bootstrap an empty database (the first revision); after that the active revision decides. Editing the files changes nothing until `config apply`. `docker compose kill -s HUP api worker` re-reads the active revision (an invalid one is logged and the previous stays active), not the files. Known gap: `aiops audit retention` still reads `AIOPS_CONFIG_DIR` for `retention_days`, like `test-connection` |
| Keycloak realm bootstrap (PKCE, CIMD, DCR switch) | Runs as Compose service `keycloak-setup`; re-run with `docker compose run --rm keycloak-setup` (set `AIOPS_DCR=on` to allow anonymous DCR) |
| Magento sandbox (Mage-OS 4.0.0, port 4390, network `aiops-sandbox`, alias `magento-sandbox`) | Up (idempotent; first run installs for a long while; also starts the `async.operations.all` bulk consumer once, `AIOPS_RESTART_CONSUMER=1` restarts it, needed after the first seed): `bash deploy/sandbox/magento/up.sh`; seed (idempotent; also 3000 `umbrella` products via async bulk; needs the consumer up.sh starts): `node deploy/sandbox/magento/seed.mjs http://127.0.0.1:4390`; admin token (24 h, prints it, keep it out of logs): `bash deploy/sandbox/magento/token.sh`; down: `bash deploy/sandbox/magento/down.sh` |
| Record the Magento preset's contract recordings (NFR-17) | Sandbox up and seeded, consumer restarted after the seed (`AIOPS_RESTART_CONSUMER=1 bash deploy/sandbox/magento/up.sh`), then `MAGENTO_SANDBOX_URL=http://127.0.0.1:4390 MAGENTO_SANDBOX_TOKEN="$(bash deploy/sandbox/magento/token.sh)" pnpm --filter @aiops/magento2-catalog record` (also records the bulk write cases of `test/write-cases.json`: changes `meta_keyword` of GLOBEX-001/002 and attempts a conflicting `url_key` on GLOBEX-001; ACME data stays untouched); the same two variables on `pnpm --filter @aiops/magento2-catalog test` also run the contract cases live |
| Log in to the trusted pages (prints the `aiops_session` cookie) | `node tooling/acceptance/page-login.mjs http://localhost:8400 carol dev-only-password`; then `AIOPS_PAGE_COOKIE=... node tooling/acceptance/page-api.mjs http://localhost:8400 session \| put-credential <ref> (secret on stdin) \| test <connection>` |
| Log in a development user (prints an access token) | `node tooling/acceptance/login.mjs http://localhost:8480 alice dev-only-password http://localhost:8400/mcp` |
| Full configuration check (specs resolved, presets loaded) | `pnpm build` once, then `pnpm aiops validate <dir> [--preset-dir <dir>]` (presets: `--preset-dir` or `AIOPS_PRESET_DIRS`, else the repository `presets/` when present; exit 0 valid, 1 invalid, 2 usage); in the image (presets at `/app/presets`, `AIOPS_PRESET_DIRS` set): `docker compose exec api node dist/cli.js validate /etc/aiops/config` |
| Test a connection (CONN-7) | `pnpm aiops test-connection <connection>` with `AIOPS_CONFIG_DIR`, `DATABASE_URL`, `AIOPS_MASTER_KEYS` set and the database already migrated; prints `ok status=<s> items=<n> ms=<d> scopes=...`, audits `connection.test` as `cli` |
| Rotate credential master keys (SEC-2) | Add the new key as the highest version in `AIOPS_MASTER_KEYS` (keep the old ones), then `pnpm aiops credentials rotate` with `DATABASE_URL` and `AIOPS_MASTER_KEYS` set; prints `rewrapped=<n> on_old_versions=<m>`; drop old keys only when `on_old_versions=0` |
| Audit chain verify (AUD-5) | `docker compose exec -T api node dist/cli.js audit verify` checks the hash chain of the sealed `audit_event` rows from the newest retention anchor: exit 0 and `ok sealed=<n> unsealed=<m> from=<pos> head=<pos>:sha256:<hex>`, or exit 1 and `failed chain_pos=<pos> reason=<reason>` (positions and hashes only, never row content); `audit verify --archive <file>` checks one retention archive against its manifest and its anchor: `ok archive count=<n> first=<a> last=<b>` or `failed archive reason=<reason>[ chain_pos=<pos>]`; needs `DATABASE_URL` (Compose sets it) |
| Audit retention once (AUD-7) | `docker compose exec -T api node dist/cli.js audit retention --now` runs the retention job once with the configuration's `audit.retention_days` and `AIOPS_AUDIT_ARCHIVE_DIR`: prints `archived first=<a> last=<b> count=<n> archive=<file>`, `nothing due` or `nothing due (audit.retention_days is not set)` (exit 0), or `refused reason=<reason>` (exit 1; `locked` while the worker's job runs); the worker also runs it at start and every 6 h |
| Audit archive directory (AUD-7) | `AIOPS_AUDIT_ARCHIVE_DIR` (absolute path; Compose sets `/var/lib/aiops/audit-archive` on api and worker, the shared volume `audit-archive`): retention writes `audit-<first>-<last>.jsonl` and `audit-<first>-<last>.manifest.json` there; unset or not writable, retention refuses and deletes nothing. Back the directory up: the archives are the only copy of the deleted rows. An archive left by an interrupted retention run (written, but no anchor committed) is an orphan: remove it and its manifest only after `audit verify --archive <file>` answers `failed archive reason=no_anchor` |
