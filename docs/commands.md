# Commands

The full command reference, moved from CLAUDE.md (ADR 0033). CLAUDE.md keeps the everyday
commands; keep this file current when a phase adds a command.

Run from the repository root. pnpm comes from the `packageManager` field through
corepack (`corepack enable` once); the user's global corepack cannot run pnpm 12
(ADR 0010). Integration and e2e tests need Docker (Testcontainers) and network.

| Configuration revisions (CFG-3, CFG-4) | `pnpm aiops config diff <dir> [--preset-dir <dir>]...` compares `<dir>` with the active revision (prints `+`/`-`/`~ <kind> <id>: <keys>` lines and `hash <old> -> <new>`; exit 0, 1 invalid or unreadable, 2 usage); `pnpm aiops config apply <dir> [--preset-dir <dir>]... [--actor <name>]` stores `<dir>` as the new active revision, audited as `cli:<name>` (exit 0, also for `No changes`; 1 invalid or a concurrent apply); `pnpm aiops config explain --operation <id> (--groups <g1,g2,...> | --service <client_id>) [--subject <s>] [--args <json>] [--records <n>]` is a dry policy evaluation against the active revision (POL-7; exactly one of `--groups` and `--service`, which evaluates a configured service account's role (AUTH-4) and refuses `--subject`): checks `--args` (default `{}`) against the input schema, then prints `effect`, `rule`, `roles`, `reason`, `detail`, and for an allowed write the `approval` line for `--records` (default 1) changes; writes nothing (exit 0 allow, 1 deny or `invalid_arguments`, 2 usage, no revision or `configuration_mismatch`). All need `DATABASE_URL`; in the image: `docker compose exec -T api node dist/cli.js config diff\|apply /etc/aiops/config` (`config explain …` likewise) (`--actor` defaults to `$USER`). Running `api` and `worker` follow an applied revision within seconds, without a restart |
| Configuration files vs revisions | Files in `AIOPS_CONFIG_DIR` only bootstrap an empty database (the first revision); after that the active revision decides. Editing the files changes nothing until `config apply`. `docker compose kill -s HUP api worker` re-reads the active revision (an invalid one is logged and the previous stays active), not the files. `aiops config explain` and `aiops audit retention` read the active revision; `test-connection` still reads `AIOPS_CONFIG_DIR` |

| Install a packed preset; version ranges; `operation_prefix` (CONN-8, OPS-5) | In the preset: `npm pack` (packs `files`: `dist`, `preset.yaml`, `spec`, the code directory), then `mkdir -p <dir>/<name> && tar -xzf <tgz> --strip-components=1 -C <dir>/<name>` and `AIOPS_PRESET_DIRS=<a>:<b>` (directories searched in order; the Docker images do this for every `presets/*`). `presets[].version` in the configuration is a semver range (absent: any); the highest satisfying version wins, ties go to the first directory. `presets[].operation_prefix` prefixes the preset's operation IDs so two presets (or two uses of one) do not collide. Preset code (`aiops.code`) is self-contained: it imports only `node:` built-ins and its own files below the code directory (no `../` out of it, no absolute `file:` URLs), and `@aiops/*` as types only (lint rule on `presets/*/src`). `pnpm aiops config diff <dir>` prints `~ preset <name>` when a preset's version or code changed |

| Review an MCP connection's tools (CONN-1, CONN-4, SEC-6) | `pnpm aiops mcp tools <connection>` lists the tools of an `mcp` connection of the active revision live, one line each: `<tool> <hash> <operation id\|-> <state\|unreferenced>`, then `listed <n> tools (dropped <d>)`; `--show <tool>` prints that tool's upstream definition for operator review only (never shown to clients) and an operation skeleton with its pin to paste into the configuration. | Audit chain verify (AUD-5) | `docker compose exec -T api node dist/cli.js audit verify` checks the hash chain of the sealed `audit_event` rows from the newest retention anchor: exit 0 and `ok sealed=<n> unsealed=<m> from=<pos> head=<pos>:sha256:<hex>`, or exit 1 and `failed chain_pos=<pos> reason=<reason>` (positions and hashes only, never row content); `audit verify --archive <file>` checks one retention archive against its manifest and its anchor: `ok archive count=<n> first=<a> last=<b>` or `failed archive reason=<reason>[ chain_pos=<pos>]`; needs `DATABASE_URL` (Compose sets it) |
| Audit retention once (AUD-7) | `docker compose exec -T api node dist/cli.js audit retention --now` runs the retention job once with the active revision's `audit.retention_days` and `sensitive_fields` (as the worker does; `AIOPS_CONFIG_DIR` is not read) and `AIOPS_AUDIT_ARCHIVE_DIR`, with `DATABASE_URL` set; no active revision, or one that cannot be loaded or has another hash, exits 2 with the `config explain` message: prints `archived first=<a> last=<b> count=<n> archive=<file>`, `nothing due` or `nothing due (audit.retention_days is not set)` (exit 0), or `refused reason=<reason>` (exit 1; `locked` while the worker's job runs); the worker also runs it at start and every 6 h |
| Audit archive directory (AUD-7) | `AIOPS_AUDIT_ARCHIVE_DIR` (absolute path; Compose sets `/var/lib/aiops/audit-archive` on api and worker, the shared volume `audit-archive`): retention writes `audit-<first>-<last>.jsonl` and `audit-<first>-<last>.manifest.json` there; unset or not writable, retention refuses and deletes nothing. Back the directory up: the archives are the only copy of the deleted rows. An archive left by an interrupted retention run (written, but no anchor committed) is an orphan: remove it and its manifest only after `audit verify --archive <file>` answers `failed archive reason=no_anchor` |
