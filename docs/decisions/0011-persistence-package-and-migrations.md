# ADR 0011: Persistence package, migrations on start, audit base schema

- Status: Accepted
- Date: 2026-11-16

## Context

[SPEC](../SPEC.md) section 3 listed no package for database code, yet both `api` and `worker`
use the same PostgreSQL schema, and the package boundaries require repository interfaces owned
by `core` with implementations outside it. NFR-5 requires forward migrations that run on start;
NFR-3 and NFR-4 allow several instances of each process, so starts can be concurrent.
AUD-1 needs an audit table from Phase 1; its hash chain (AUD-3) is Phase 8.

## Options considered

1. Database code location: in `apps/api` (worker would import an app), duplicated in
   both apps, or a new `packages/db`.
2. Migration runner: a one-shot Compose service; Drizzle's `migrate()` as is in each
   process; `migrate()` inside a session holding a PostgreSQL advisory lock.
3. Append-only enforcement before Phase 8: code convention only, or a trigger.

## Decision

- **New package `packages/db`** (`@mandate/db`): Drizzle schema, committed SQL migrations
  generated by `drizzle-kit`, `runMigrations`, connection factory and the
  implementations of `core` ports (Phase 1: `DrizzleAuditLog`). SPEC section 3 is
  amended accordingly.
- **`runMigrations`** takes `pg_advisory_lock` on a dedicated `pg.Client`, runs Drizzle's
  `migrate()` on that client, and unlocks in `finally`. `api` calls it before it
  listens; `worker` will call it from the phase in which it first uses the database.
- **Audit base table `audit_event`** with an identity `seq`, application-generated
  UUID `id`, the AuditEvent fields of SPEC section 4 plus `client_id`, `outcome`,
  `changeset_id`, `details` (jsonb), and nullable `prev_hash`/`hash` for Phase 8. A
  trigger rejects `UPDATE`, `DELETE` and `TRUNCATE`. AUD-7's retention adds its own
  path in a later migration.

## Consequences

- Drizzle decides what to apply by comparing each migration's journal timestamp with
  the **latest applied** one only. A migration whose timestamp is older than the last
  applied one is skipped silently. Never hand-edit journal timestamps; never merge a
  branch whose migration was generated before one already on `main` without
  regenerating it.
- The advisory lock key is a fixed constant in `packages/db`; nothing else may use it.
- A trigger-based append-only rule means tests cannot clean the table; integration tests
  use a fresh database per suite.

## Verified

2026-11-16, `drizzle-orm@0.45.4` source in `node_modules/drizzle-orm`:
`node-postgres/migrator.js` only reads the files and calls `dialect.migrate`;
`pg-core/dialect.js` `migrate()` runs `CREATE SCHEMA IF NOT EXISTS`, `CREATE TABLE IF
NOT EXISTS`, reads the latest row by `created_at` **outside** its transaction, then
applies every migration with `folderMillis` greater than it in one transaction. No lock
is taken, so two concurrent runs can both apply the same migration. The concurrency
test in
[`packages/db/test/integration/migrate.int.test.ts`](../../packages/db/test/integration/migrate.int.test.ts)
(`NFR-5`) shows the locked runner is safe.
